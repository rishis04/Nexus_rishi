# Security Model

Antigravity employs a strict zero-trust model designed to isolate the unverified LLM Planner from the local execution environment.

## Key Boundaries

### 1. The Minimum Disclosure Principle
The DOM is never sent to the LLM directly. Instead, the `PerceptionContract` is heavily redacted on the client side:
- Image redaction masks areas matching PII definitions (e.g., face detection).
- Text redaction replaces sensitive strings (e.g., Aadhaar, PAN) with anonymized tokens before egress.

### 2. The Local Action Firewall
All actions generated by the remote Planner are inherently untrusted. 
Before an action executes, the `TargetValidator` enforces:
- **Origin & Frame Validation**: Actions must target the same domain and frame where the original element was perceived.
- **State Fingerprinting**: A SHA-256 hash of the DOM is verified. If the page layout or state has shifted (e.g., an ad popped up), the action is rejected as a "stale state" to prevent accidental clicks.
- **Occlusion Defense**: Target bounding boxes are checked against `document.elementFromPoint()`. If the element is hidden, zero-opacity, or covered by a z-index layer, the action is blocked (Clickjacking defense).

### 3. Local Secret Capability System
The LLM Planner is completely unaware of raw credentials.
When an action targets a password field, the system intercepts it:
- The Planner simply emits an action with `secret_ref: "vault://login/github.com"`.
- The Extension Vault resolves this locally using AES-GCM.
- It checks `allowed_origins` to ensure the vault secret is authorized for the current domain.
- The decrypted password is typed directly into the input via the Chrome Debugger API, entirely bypassing the network and extension state payload.

### 4. Attestation and Integrity
Each `StructuredAction` from the Planner must be cryptographically signed by the trusted execution environment to prevent man-in-the-middle (MITM) tampering. Unsigned or invalid payload actions are dropped.
